## Scope and evidence

Audited fetched `origin/main` at `64e2a2466b6146bc2d2c8e9934294fa7a52170c1`. The performance branch starts there; gameplay branches are stacked separately on it. **OBSERVED:** the game is a React UI around a canvas engine, with 14 maps, 21 species, level-based starter evolutions, turn-based combat, local v2 saves and a four-creature party. The previous repository audit is historical, not proof that current behavior was exercised.

**VERIFIED:** The original focused tests reproduced stale toast display, false save success, accumulating audio listeners and forced-switch selection. Fixes have focused regression tests. The test journey opened the game, started a new save, advanced the introduction, walked in the house, saved, and used an existing diagnostic probe to reach two outdoor maps and a wild battle. Probe-assisted scenes are not evidence of natural progression or a complete playthrough.

**VERIFIED:** On this Windows host with Node 24.22.0, Edge 156 headless, unthrottled, five-second samples at 1280×800 and 390×844 produced 59.61–60.01 FPS, p95 16.8–17.0 ms, p99 17.1–17.5 ms, and no frame interval above 50 ms. The 59.61 sample is below a literal 60 FPS: no universal 60 FPS claim is established. The browser's scheduler and display configuration limit what these numbers prove. Each sample contained 298–300 rendered frames. Initial outdoor scenes averaged 215–314 visible canvas image draws per frame; cached terrain and culling reduced them to 5–9 in comparable scenes. This is a draw-call reduction, not a measured FPS speedup: baseline was already approximately 60 FPS. Battle remained three draws per frame.

Raw frame intervals and screenshots are local task evidence in `D:/AgentData/evidence/reliquary/20261026/{baseline,foundation}`; they are not committed. The baseline and foundation captures used the development server, not a production build or real mobile hardware. Asset loading, physical devices, long sessions, high refresh rates, audio quality, full battle balance and the complete route remain open checks. A cache can trade lower per-frame work for map-change and memory cost; measure both on representative devices.

**VERIFIED, visual comparison:** The baseline and cached-render Wildwood screenshot files are byte-identical at each tested viewport, as confirmed by SHA-256. ## Chapter-one campaign — October 28, 2026 (`feat/chapter-one-20261028`)

This slice was implemented on `feat/chapter-one-20261028`, based on `origin/codex/gameplay-raising-20261026` (the head of the stacked PR #12 line). Its goal was to make the natural first-chapter journey — start, starter pact, wild binding, party growth, Warden trial, save/reload — completable, understandable and fair.

**VERIFIED, objective recap:** A pure `currentObjective(flags)` system drives a HUD hint line (initially: speak a pact at the Binding Grove; after the start: bind on the way and take the Wildwood north to Warden Cael; after the trial: the Hollow Crown waits) plus a full-length objective line in the root menu. Covered by focused tests and visible in every chapter journey screenshot.

**VERIFIED, learn-or-decline skill choice:** Level-ups at a full four-slot move list no longer silently replace index 3. The learned skill is queued as `pendingSkills` on the beast (save v2 schema extended, optional field, semantically validated), announced as a toast, and resolvable from the Party card: replace a named skill or decline, with chained queues offering one skill at a time. Focused tests cover queue persistence, replace, decline, save round-trip and semantics; the browser fixture journey performs both flows with keyboard and verifies the saved state.

**VERIFIED, Pack targeting:** Field Pack no longer targets `party[0]` blind. Selecting a usable item with more than one eligible beast opens an eligible-target list with current HP and an effect preview; single-candidate uses skip straight through; no-effect uses still never consume anything. Focused tests cover selection, cancellation that returns to the chosen pack item, phoenix-ash revival and preview data; journey coverage exercised the target list in a portrait-size touch-flow and via engine tests.

**VERIFIED, combat statuses mean something:** `bind` now sends the bound beast last in turn order and prevents fleeing; `daze` is a 25% chance to fumble the turn. Both keep the ×1.4 binding-stone bonus. Each application is announced with plain language ("is bound now", "grip fumbles") and a Wayfarer dialog page explains all statuses. Deterministic order of play tests cover turn order with binding, daze fumbling, the flight block and the foe mirror.

**VERIFIED, inn rest is a choice:** The innkeeper prompt states the price and shows the dialog convention (`A rest · B not now`), cancel skips the rest and never charges, insufficient crowns produce a refusal without spending. Focused engine tests cover confirm, cancel and low-gold paths; journey coverage includes the cancel path.

**VERIFIED, Warden trial guidance:** Cael's pre-trial dialogue telegraphs his team (Iron. Chapel. Drake.), offers an explicit begin/decline convention, and when the strongest companion is below twelve levels pages in explicit advice that a stronger compact goes lighter. Advocacy is advice, not a gate; the decline path starts no battle.

**VERIFIED, party and storage reachability:** Party and Storage card actions are reachable with directional keys or the touch pad alone. Arrows highlight cards, A opens a per-card action submenu (make lead, practice, learn, store, add to party, rename — context-filtered; unaffordable Practice is hidden), B backs out one step at a time, and Rename opens the existing form with focus. Focused engine tests cover open/action/banner-highlight/cancel for party and storage including lead reordering; the fixture journeys drive the store, learn and rename flows with arrows and A only.

**VERIFIED, continue robustness:** `Continue` with an unreadable stored save now reports the loss as a dialog page on top of a new opening rather than silently restarting. Focused test covers the path.

**VERIFIED, chapter-one acceptance journeys (`feat/chapter-one-20261028`):** All journeys ran against the development server on this Windows host (Node 24.22.0, msedge 156 headless via Playwright). `scripts/chapter-one-qa.mjs` completed the natural journey with no warps, no fixture saves and no engine probes, seeding only keyboard/keypad input and, at the bind moment, `Math.random` to land the capture: introduction in the Warden's cottage → Maren in Elderhall → the Grove → Emberkit pact (objective line advanced) → Briar Road → a wild Mothwisp appeared and was bound; the party sheet showed two creatures; card actions practiced Emberkit (80-lore toast; no level-up at that threshold), renamed the Mothwisp to "Fogmote" through the card menu; the inn prompt was declined with B (gold unchanged, dialog closed) and then accepted (15 crowns spent, full heal, rest dialog); Menu → Save ("The lantern remembers."); reload → Continue → both Emberkit and Fogmote present in the party sheet with the objective line intact. `scripts/chapter-one-fixture-qa.mjs` used explicitly labeled fixture saves (probe-assisted, not the natural journey) to cover: learn-choice replace/decline persisted through reload; a seeded lost battle whiteout (gold 200→170, Elderhall return dialog); Cael's advisory and decline path at a sub-12-level party; and the Warden trial won end-to-end through real UI clicks — three foes in sequence, a forced switch after a faint, tonic use, Thorn Mark in the verified save (3 thorn_sigil; at least 2 greater_tonic), epilogue, reload with the post-trial objective. ## Current work slices

The performance branch contains the terrain cache, lifecycle/save fixes, combat repairs and QA harness. Separate stacked branches add progression visibility and nickname preservation; party lead selection; storage transfers; creature naming; and 80-lore practice for 45 crowns. Practice uses existing gold, lore and save fields; its cost/reward is an initial balance assumption, not a tested economy. Evolution, nicknames, storage and practice require complete browser journeys and independent review before they are represented as release-ready. Stacking means later gameplay branches include earlier ones; compare each branch with its immediate parent to review only that slice.

## Repeatable acceptance loop

1. For a specific issue, record revision, device, browser, reproduction steps, expected/actual result and a test that fails on the original defect.
2. Make the smallest repair. Run the focused regression, gameplay/content tests, typecheck, lint and build as required by the candidate.
3. Replay the same user journey at desktop and portrait sizes; inspect logs and screenshots. Include no-save, failed-save, no party, full party, fainted party, low gold, empty inventory and touch/keyboard paths.
4. Record uncapped frame intervals over repeated warm and cold runs, transitions, movement and active combat. Require real successful work, device/browser/GPU details, error counts, p50/p95/p99 and stall counts. Never compare a fast error or hidden/no-op canvas as a performance win.
5. Reassess the highest player-impact defect, update this ledger and repeat. Establish the target device class and a meaningful allowed variance before making a release-level 60 FPS claim.
